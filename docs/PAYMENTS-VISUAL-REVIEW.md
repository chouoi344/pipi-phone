## QA hooks and verification handoff

- New `walletTransaction(id, back, { fromChat: true })` selects the message summary. Existing calls without the third argument still open the accounting detail.
- `.wallet-pay-page`, `.wallet-pay-recipient strong`, `name=amount`, `.wallet-pay-confirm`, `.wallet-pay-disclosure`, and red-packet `name=note`/`#redpacket-total` remain.
- Transfer description now uses `#transfer-note-editor` → `#transfer-note-draft` → `#transfer-note-save`; `[data-note-cancel]` cancels. Its submitted `name=note` is hidden and receives only the confirmed value.
- Message detail retains `.wallet-transaction-detail`, `.wallet-detail-amount`, `.wallet-detail-note` and `.wallet-detail-status`, plus `.payment-message-detail.is-transfer-detail` / `.is-redpacket-detail`. In message summaries the amount text is `2.34` / `1.23`; currency/unit are adjacent elements. Bills retain their signed amount text.
- `#payment-detail-bill` opens the accounting detail. `.wallet-detail-fields` exists only there, and Back returns to the previous summary.
- `node --check public/features.js` was run after the structural edits and passed. Final independent UI/amount/navigation outcomes belong to the QA report; this document does not predeclare them passed.

The v0.4.1 screenshots were directly inspected for composition, both cards and both detail screens at DPR3. The independent payment diagnostic subsequently passed its two checks (setup plus the complete payment scenario), and its eight payment images in `%TEMP%/pipi-ui-v042-payment-diagnostic` were directly opened: transfer composition, note dialog, both cards, red-packet composition, both message summaries and the transfer bill. Visual inspection caught a real bug that the functional assertions did not: the global margin reset placed the new dialog at the upper-left corner. Explicit fixed insets/auto margins now center it, with maximum height and scrolling; QA was asked to add a geometry assertion and recapture it in the final run. This diagnostic is not the final all-screen test result.

Font rendering on Windows remains Noto Sans SC, whereas the actual iPhone uses its platform fonts. No amount of passing server/DOM tests removes that native rendering limitation.

## Final screenshot closure

The following final DPR3 files in `%TEMP%/pipi-ui-v042-final1` were opened again after integration and the dialog correction: `390-chat-transfer.png`, `390-chat-transfer-note-dialog.png`, `390-chat-redpacket.png`, `390-chat-transfer-card.png`, `390-chat-redpacket-card.png`, `390-chat-transfer-detail.png`, `390-chat-redpacket-detail.png` and `390-chat-transfer-bill-detail.png`.

- The note dialog is now centered horizontally and vertically in the 390×844 viewport; title, input and both actions are fully visible. The independent geometry assertion also passed. The earlier upper-left diagnostic image is obsolete.
- The orange transfer card now uses the distinct 40×40 icon hook; the red-packet icon uses its 32px width. This is an actual rendered artwork check, not only an SVG-box inspection. The envelope remains the attributed original line symbol, not a verified proprietary WeChat cover image.
- Long test descriptions and blessings are intentionally ellipsized on the compact single-line cards. The full `HEADLESS_TRANSFER_NOTE` and `HEADLESS_RED_PACKET_NOTE` values are visible in the corresponding detail screens. Amount/currency and the virtual sending status are readable. No amount is exposed on the red-packet card.
- The transfer detail, red-packet detail and accounting detail visibly differ in hierarchy. The bill keeps signed accounting values and metadata; the message summaries use amount/currency or amount/unit. No claimed/accepted/refunded state appears.
- No new blocking overlap, missing control or clipping was found in these eight 390px payment captures. This is a bounded visual review, not a claim of exact 8.0.80 fidelity.

Static checks of the integrated CSS confirm that transfer recipients and detail notes can wrap (`min-width:0`, `max-width:100%`, `overflow-wrap:anywhere`), the note dialog has a height limit/scrolling, and the page editor reserves the outer safe area once. These checks are **not** a rendered long-recipient or narrow-payment acceptance test. This screenshot set contains no separate 320px payment, payment-specific simulated-safe-area, enlarged-payment-text or real iPhone keyboard captures. Root-page safe-area and enlarged-text results must not be generalized to those missing payment states.

The first final all-screen run reported 40/41 checks, with the separate pre-existing search/IME test preparation race being rerun without product changes. Payment checks passed within that run; the final aggregate result is owned by the independent QA report. No product code was changed during this closure review.

## Supplemental narrow/landscape payment check

The previously missing narrow payment states were subsequently tested independently. The final targeted run in `%TEMP%/pipi-ui-v042-payment-responsive3` passed **2/2** checks (isolated setup plus the payment adaptation scenario), covering both payment types at 320×568 and touch-landscape 844×390. The latter explicitly simulates left/right insets of 47px and bottom inset of 21px. Fixtures contain a 60-character recipient name and a 60-character note/blessing. The original strict overflow assertion was retained, as were actual hit tests after scrolling the amount, confirmation, note-dialog actions, detail note and bill entry into view. Stored notes and exact amount submission were also checked.

An initial reported shell width of 358px at a 320px viewport was investigated before changing product CSS. Geometry showed the existing page-entry animation at `translateX(38.4px)` (`320 × 12%`), with its animation running at time zero. Waiting for that actual animation's completion restored the strict overflow assertion. The same timing applied when entering message detail. This was a transient measurement of the intentional transition, not a persistent long-recipient layout defect; no product clipping/overflow workaround or weakened assertion was introduced.

The ten `payment-adapt-320-*` and `payment-adapt-844-*` captures were reviewed, including the final 320/844 transfer and red-packet detail images. Recipient/note content wraps inside the available width; long content scrolls under the fixed header, so one screenshot need not show the entire page at once. Note dialogs remain centered and readable, submit actions remain reachable, and landscape content respects the simulated side insets. No stable-layout payment blocker was found in these captures. Enlarged payment text, real OS keyboard behavior and version-bound 8.0.80 pixel matching remain outside this test's evidence.

# 水滴皮肤整机验收方案

用户已确认。分组、图标和玻璃外观按水滴版参考验收；切页、菜单、弹窗和按钮响应同时验微信经典版与水滴版。首次进入从启动画面起就显示经典版，已有选择的浏览器恢复上次的皮肤。

公开方案用于确定验收方法。微软 Playwright 的验收规划智能体从真实操作发现入口，记录成功和失败条件；本次据此清点控件并走完整条操作路径。Chrome Lighthouse 的交互流程建议按一次切页或一段操作单独录制；本次据此比较相同条件下的开合速度。Deque 的 axe-core 说明隐藏的菜单、弹窗要展开后检查，因此每类浮层都在打开状态另做视觉和键盘核对。[Playwright 验收规划智能体](https://github.com/microsoft/playwright/blob/main/packages/playwright/src/agents/playwright-test-planner.agent.md) · [Lighthouse 用户操作流程](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md) · [axe-core 检查范围](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)

## 一、先用三张反馈图定下标准

| 用户能看到的地方 | 实际怎么验 | 通过时应看到什么 |
| --- | --- | --- |
| 图一，微信首页会话分组 | 用隔离资料准备多条会话，分别试零置顶、部分置顶、全部置顶。实际置顶、取消置顶、收新消息、切「未读」和「置顶」、返回首页、刷新。 | 上卡收纳全部置顶会话，下卡收纳全部普通会话。每组只有一圈外轮廓和一对上下圆角。空组收起，组内沿用实际会话顺序。「全部」里没有置顶时，几条普通会话连成一张卡。 |
| 图二，右上加号和菜单 | 合上和打开各看一次，核对加号、四个菜单图标、文字基线、点击区域、浮层位置。每一行点进去，再返回；首次点外侧可收起。 | 图标只有一层清晰轮廓，加号位于圆钮中央。菜单采用参考中的浅色透光面板、圆角与轻阴影。四个原有操作可辨且好点，快速开关也不会留下遮罩。 |
| 「我」页的皮肤入口 | 将「皮肤」与同组的收藏、朋友圈、人设、表情并排对照，再看皮肤选择页。 | 同级入口的图标尺寸、线条、色彩饱和度和文字对齐协调；入口用普通导航样式。选择页才用选中标记清楚表示正在使用的皮肤。 |
| 图三，底栏露出半行文字 | 在通讯录初始位置、慢慢滚动和滚到底分别观察「几个朋友」。四个主页，以及带固定保存栏、输入栏、键盘或底部弹窗的子页，都用短内容和长内容复查。 | 底栏及它下方的留白区看不到半截字、行尾或可点击控件。滚到底能完整读到最后一行并点到最后一项。浮起的外观和安全留白仍然可见。 |

参考示例在源码中明确标了「置顶卡片分组」和「普通会话卡片分组」，加号菜单有独立的浅色透光样式。验收按真实会话的置顶状态分组。[会话卡片参考](../../微信液态玻璃美化包参考/wechat-miniapp-demo.html#convScrollList)

## 二、从四个主入口把实际按钮清点到底

先从微信、通讯录、发现、我逐级展开，在每个页面登记可见按钮、长按或侧滑动作、折叠区、更多菜单和条件出现的入口。再与当前程序的页面、弹窗和按钮清单交叉检查，补出空资料、未读、未配置、待领取或编辑中才出现的操作。同一个按钮从两个不同页面进入时，两条返回路径都核对。相同结构的多条会话按数据状态取样。

| 从哪里进入 | 要点到哪里 |
| --- | --- |
| 微信 | 筛选、搜索、加号四项、置顶和会话侧滑；聊天文字、表情、语音、语音转文字、工具各页、消息长按、引用、聊天背景、聊天信息；红包和转账的填写、详情与处理后状态。 |
| 通讯录 | 搜索、字母索引、顶部分类、好友资料和资料设置；角色配置八个分类及每个分类下可操作的字段、开关、单选、多选、编辑、上传和保存。 |
| 发现 | 朋友圈、发布与评论、发现下的功能和管理入口、发语音配置、工具子页；持续下钻至该入口能打开的最后一层。 |
| 我 | 个人资料、状态、服务、钱包与账单、收藏、人设、皮肤、表情、设置；从实际菜单下钻到模型、用量等自制页及其选项弹窗。 |

每项登记「入口路径、按钮、前置状态、预期、实际、证据、结果」。结果使用通过、失败、待验证。打开原有功能说明页的入口，分别记录说明页展示、返回，以及该功能当前的可用范围。涉及保存、删除、领取、退还和失败重试的操作，使用可恢复的隔离资料和本机模型。

## 三、每个入口怎样才算通过

1. **看得清、点得准。** 对照同层级文字的字形、字号、粗细与换行，核对图标线条、图标和文字的中心、卡片边界、颜色和选中状态。返回、加号、关闭等常用独立按钮以 44 × 44 个网页像素的有效点击区为项目目标，同时点中心和边缘，检查是否误触邻项。[W3C 点击目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
2. **点下去有正确结果。** 每个可用按钮真实点击并核对结果，禁用按钮检查何时启用。编辑类检查空白、填写、清空、取消、保存和刷新回读。返回后应找得到刚才的项目，列表位置与草稿按已有规则保留。功能覆盖以用户实际能完成的操作为准。[Playwright 官方测试实践](https://playwright.dev/docs/best-practices)
3. **弹窗从打开验到退出。** 首次打开、再次打开、点外侧、点内部、滚动到底、确认、取消逐项检查。嵌套弹窗只关当前一层，遮罩挡住背后的按钮；打开键盘时能看到当前输入与确认按钮。电脑检查键盘导航与关闭后焦点返回。底栏遮挡用实拍与滚动位置共同判断。[W3C 弹窗交互](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) · [W3C 固定栏遮挡说明](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum)
4. **切皮肤后仍能完成原操作。** 从「我 → 皮肤」切换、刷新、返回，确认经典版和水滴版各自正确。核对自选聊天背景、AI 等待与分段回复、系统减少动态效果，确保本轮性能优化保留上一版已确认的质感和行为。

## 四、把「点着慢」和「动起来卡」分别测

优化前先留一份基线。优化前后用同一浏览器、同一窗口大小、同一批隔离数据、同一套操作。普通手机宽度 390、窄屏 320、电脑宽度 1280；手机再以浏览器四倍处理器减速模拟较慢设备。单独标明模拟环境和可用的实体设备。

| 记录什么 | 怎么测、怎么判断 |
| --- | --- |
| 点下至首个可见反馈 | 常用路径每条记录首次打开，并在预热后重复十次，列出典型值、最慢一次和超线次数。正常环境拟定目标为十次中至少九次在 200 毫秒内有可见反馈。首次打开单列，超过 200 毫秒也要定位。模型请求另计等待时间，先验按钮按下和等待状态是否及时出现。这里的数字是本轮本地操作目标。[Google 响应速度说明](https://web.dev/articles/inp) |
| 动画中途是否停住 | 录制四主页面互切、聊天进出、加号菜单、工具面板、底部选择、长表单和键盘开合。记录相邻画面的间隔，回放最慢片段。60 Hz 屏幕正常每帧约 16.7 毫秒；将正常环境重复出现的超过 50 毫秒停顿，以及可重现的闪白、跳位、倒放或残留遮罩列为待修。减速环境单列，交代慢在哪里和前后差异。[Google 动画性能指南](https://web.dev/articles/animations-guide) |
| 连续操作会怎样 | 快速切换三次、连点开关、弹到一半返回、列表滚动中打开详情、输入中切换面板。通过时最后一次操作正确生效，无双开、重复提交、吞点击或滚动突然跳顶。 |

根据录制结果决定改哪一层。若卡在页面构建，优先减少重复建页；若时间花在绘制，再缩小玻璃模糊、阴影或页面快照的重绘范围。保留参考中可感知的水滴高光、弹出方向与 AI 回复节奏，以同条件前后回放确认改善。

## 五、独立验收与交付

1. 实施者先跑完按钮清单，对失败项修复并复测。交给验收员的材料包括三图同尺寸前后对照、按钮覆盖清单、最慢交互的录制或时间记录。
2. 第一位独立验收员从真实入口复现用户提出的问题，按清单找缺陷。每个发现保留路径和证据，修复后由发现人复验。
3. 第一轮通过后，第二位独立验收员从界面自行找入口，再和清单反查遗漏。重点挑战窄屏、长列表、条件按钮、嵌套弹窗、连续进退及慢设备。新增问题同样修复、复验；若修复涉及第一轮已通过的共享控件，请第一位补验受影响路径。
4. 两轮在最终交付版本上通过、已发现的范围内问题均关闭后，打开内置浏览器，停在已选水滴版的验收预览。交付时给出覆盖数、发现及修复、耗时前后对照、实际测试设备，以及仍需用户判断的真机体感。

本轮的实际操作、计时、截图和验证范围见[整机验收记录](../../.codex/validation/waterdrop-polish/验收结果.md)。

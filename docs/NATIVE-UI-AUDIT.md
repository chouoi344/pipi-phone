## 判定顺序和业务边界

1. 用户当前提供的真实 iPhone 微信截图最高；用户提供的 Android 模拟器是已认可参照。已直接查看 945×2048 真图，仅可确认这张截图中出现的页面与状态，不外推其他页面当前版本的精确样式。
2. 已获许可的项目给出可复用的 DOM/组件结构和历史交互依据。WeChatSwift/CoderMikeHe 多为旧版，fake-world 是仿制工具，均不是当前原生微信的真实性证明。
3. 模型、角色、人设、记忆和主动活动仍只放在「我 → 设置」。本轮处理原生页面结构、状态、返回和已确认业务的真实可用性，不做个性化美化。
4. 群聊、扫码、拍摄、视频/位置/文件/名片发送、卡券、音乐、礼物、公众号等只保留合理入口并明确暂未开放；不能为了入口还原引入新后端业务。虚拟红包/转账/流水属于既有真实业务；银行支付、充值、提现不实现。

## 实施后的最低复核顺序

1. 390×844：从每个root依次进入实际二级页，逐页截全屏；同一页面同时截普通/展开/编辑/返回状态。补320px窄屏防溢出；真机软键盘另记。
2. 表情：空内容禁用发送；输入中间插入；删一完整表情；切分类/分页；面板发送；从系统键盘切换；最后消息与composer的相对位置正确。
3. 红包/转账：分别截图填写空/有效/不足余额/成功卡片；0/小数/重复点验证；取消、Escape、系统Back各回到同一个原会话，不能显示钱包中间页；虚拟余额与流水一致。
4. 好友资料 → 好友朋友圈 → 返回好友资料；Me → 自己朋友圈 → 返回Me；发现 → 全部时间线。三个上下文互不串台。
5. 搜索结果命中老消息后定位；返回保留词与结果；在历史位置收到刷新不跳底。朋友圈打开评论再离开，body上无遗留输入条。
6. 不把现有API通过和DOM元素存在当视觉通过。缺真实参考的页面必须标待校准；未开放入口只验证提示，不记录为真实功能已完成。
